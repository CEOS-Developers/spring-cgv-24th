# 완료 결제 조회와 데이터 저장 기준

## 기존 상태와 추가한 기능

기존에는 승인 처리 중 Toss 결제를 조회하는 내부 메서드만 있었습니다. 사용자가 본인의 완료 결제를 조회하는 API는 없었습니다.

추가한 기능:

- `GET /api/payments/{paymentId}`: 본인의 승인 결제 상세
- `GET /api/payments?page=0&size=20`: 본인의 승인 결제 목록
- 전체·부분 취소 후에도 조회 가능: `approvedAt`이 있는 `DONE / PARTIAL_CANCELED / CANCELED`
- 주문명·통화·검증한 결제 수단 저장
- 승인 결과의 `paymentKey, orderId, totalAmount, currency` 일치 검증
- 본인 확인과 완료 상태를 DB 조회 조건에 포함

요청·응답 예시는 [API 명세서](api-spec.md#결제)에 정리했습니다.

## 우리 서비스가 저장하는 정보

| 데이터 | 저장 이유 | 값의 출처 |
| --- | --- | --- |
| `paymentId` | 우리 서비스 결제 식별 | 우리 DB |
| `userId, targetType, targetId` | 결제 소유자와 예매·매점 주문 연결 | 인증 정보와 우리 주문 |
| `orderId` | PG와 연결하는 고유 주문번호 | 서버 생성 |
| `orderName` | 결제 시점 주문명 보존 | 서버에서 구매 종류별 결정 |
| `amount, currency` | 청구 기준 보존·PG 응답 대조 | DB 가격으로 계산, 현재 KRW |
| `balanceAmount` | 여러 번의 부분 취소 후 남은 금액 | 승인 시 원금, 검증된 취소 시 차감 |
| `status` | 서비스의 결제 처리 상태 관리 | 검증한 PG 결과 및 서비스 상태 전이 |
| `paymentKey` | 장애 시 PG 조회 및 추후 취소 연동 | Toss 인증·승인 과정 |
| `paymentMethod` | 결제 내역 표시 | 검증한 Toss 승인 응답 `method` |
| `createdAt, expiresAt` | 결제 준비·유효기간 관리 | 서버 |
| `approvedAt` | 승인 시각 기록 | 검증한 Toss 승인 응답 |
| `confirmIdempotencyKey` | 동일 승인 재시도 제어 | 서버 생성 |

각 취소 요청은 별도 `PaymentCancellation`에 요청 키·PG 멱등키·요청 금액·확정 취소 금액·이전 잔액·사유·상태·PG 거래 키·시각을 저장합니다. `canceledAmount`는 원금에서 잔액을 뺀 파생 값이며 중복 저장하지 않습니다. 자세한 내용은 [결제 취소 구현 안내](payment-cancellation.md)를 참고하세요.

금액은 브라우저가 보낸 값으로 덮어쓰지 않습니다. 주문명도 PG 응답이나 이후 변경된 상품 정보로 덮어쓰지 않습니다. 지금 주문명은 `영화 티켓 예매 / 매점 상품 주문`이며, 영화 제목이나 메뉴 이름까지 보존하려면 준비 단계의 주문명 생성 로직을 확장하면 됩니다.

조회 응답에는 표시·연결에 필요한 필드만 반환합니다. `paymentKey, confirmIdempotencyKey, userId`는 반환하지 않습니다. 시크릿 키, 카드 전체 번호, CVC, 비밀번호, 불필요한 원본 PG 응답은 결제 테이블에 저장하지 않습니다. 영수증 URL 등은 현재 화면 요구사항에 없어 저장하지 않았습니다.

Toss의 `paymentKey`, `method`, `currency`, 승인 시각 등의 의미는 [Toss Payments Payment 객체](https://docs.tosspayments.com/reference)를 기준으로 삼았습니다. 이번에 추가한 필드는 전체 PG 응답 중 조회와 검증에 필요한 일부입니다.

## 조회할 때마다 PG에 요청해야 할까?

**일반적인 결제 내역 조회는 우리 DB만 사용하도록 구현했습니다.** PG 호출 지연·장애가 사용자의 과거 내역 조회에 영향을 주지 않으며, 사용자 소유권과 예매·주문 연결 정보도 우리 서비스가 관리할 수 있습니다.

`PaymentQueryService`는 결제·취소 이력 Repository만 사용합니다. Toss 클라이언트를 호출하거나, 조회하면서 결제 상태를 변경하지 않습니다. 승인 성공 시 결제 완료와 예매·주문 확정을 같은 트랜잭션에서 저장하고, 취소도 검증 후 잔액·이력·대상 주문 변경을 같은 트랜잭션에서 저장합니다.

PG 통신이 필요한 작업은 따로 있습니다.

- 결제 승인 및 전체·부분 취소 요청
- 승인 응답 유실로 결과가 불명확할 때 실제 결과 확인: 기존 승인 서비스에서 처리
- 웹훅 이벤트의 결과 확인·반영 또는 주기적인 대사: **아직 미구현**

DB 조회만으로 PG와 자동 동기화되는 것은 아닙니다. PG 관리자 화면에서 별도로 취소하거나 비동기 상태 변경이 생기면 로컬 완료 기록이 실제 상태와 달라질 수 있습니다. 향후에는 [Toss 웹훅](https://docs.tosspayments.com/guides/v2/webhook)과 결과 검증·대사 처리를 추가하고, 검증된 변경만 중복에 안전하게 반영해야 합니다. 이때 사용자 GET 요청에 동기화 책임을 넣지 않는 것을 권장합니다.

## 역할 구분

| 우리 서비스 | PG사 |
| --- | --- |
| 누가 어떤 예매·매점 주문을 구매했는지 관리 | 카드사 등 결제망과 실제 승인·취소 통신 |
| 좌석·재고·가격·주문 상태·결제 유효기간 관리 | 결제 인증 및 PG 거래 결과 관리 |
| 승인 결과를 검증하고 서비스 주문을 확정 | 결제 수단별 처리 및 정산 정보 관리 |
| 사용자별 결제 내역 제공, 서비스 기록과 PG 결과의 일치 관리 | 결제 조회·웹훅 등으로 거래 결과 제공 |

PG 거래의 실제 결과는 PG에서 확인하고, 우리 서비스는 그 결과를 검증해 주문 상태와 연결합니다. `DONE`이라는 문자열 하나만으로 좌석·재고 처리를 대신할 수는 없습니다.

## DB 적용

기존 로컬 테스트 DB에는 [payment-history-migration.sql](../scripts/sql/payment-history-migration.sql)을 **한 번** 적용합니다. 이 스크립트는 `cgv_payment_test` 전용입니다. 다른 DB에서는 대상 이름과 기존 스키마를 먼저 확인해야 합니다.

- `order_name, currency, payment_method` 추가
- 기존 결제의 주문명과 KRW 통화 보완: 이전 코드가 사용한 고정값
- 기존 `payment_method`는 근거가 없으므로 `NULL` 유지
- 본인 완료 결제 조회용 `(user_id, status, approved_at, payment_id)` 인덱스 추가

이번 작업에서 로컬 `cgv_payment_test`에 적용했으며, 기존 결제 2건이 보존된 것을 확인했습니다. 실행 중인 서버에는 코드 변경이 자동 반영되지 않을 수 있으므로 `payment-test` 프로필로 재시작한 뒤 요청하세요.

기존 결제 수단까지 채우고 싶다면 검증된 PG 조회 결과를 이용한 별도 일회성 보완 작업이 필요합니다. 일반 GET에서 자동으로 PG에 요청하거나 임의로 `카드` 값을 넣지는 않습니다.

## 검증

`PaymentQueryIntegrationTest`에서 다음을 검증합니다.

- 본인 예매·매점 승인 결제 조회 및 타인 접근 차단
- 미완료 상태 제외와 빈 목록
- 페이지 범위, 정렬, 페이지 분할
- 인증 없는 접근 차단
- PG 클라이언트가 장애 상태여도 로컬 조회 성공, 조회 중 PG 호출 없음
- PG 키와 내부 멱등 키가 응답에 노출되지 않음

승인 통합 테스트에서는 결제 수단 저장과 통화 불일치 시 완료 처리하지 않는 동작도 검증합니다. 테스트에서는 Toss 클라이언트를 모킹하므로 실제 PG 승인 요청은 전송하지 않습니다.

취소 구현 이후에는 [payment-cancellation-migration.sql](../scripts/sql/payment-cancellation-migration.sql)도 적용해야 합니다. 이번 작업에서 로컬 테스트 DB에 적용했으며 기존 결제 2건을 보존했습니다. 취소 통합 테스트에서는 환불·잔액·중복·동시 요청·장애 복구를, 클라이언트 테스트에서는 로컬 가짜 PG 서버로 실제 HTTP 요청 형식을 검증합니다.
